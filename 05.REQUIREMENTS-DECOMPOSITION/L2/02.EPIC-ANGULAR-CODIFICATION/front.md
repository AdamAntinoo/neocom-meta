# EPIC-002 - ANGULAR CODIFICATION — front

Extracted from `L1/02.EPIC-ANGULAR-CODIFICATION.md`. The model is `neocom-infinity-frontend/src/app`.

## UNREGISTERED REQUIREMENTS

- A page is a routed screen. A panel is a piece of a page and has no route of its own. A section of the application is an Angular module under `app/modules` that owns the pages and panels of that section. The root router loads a section with `loadChildren`. The section module registers its routes with `RouterModule.forChild`.

- `app/pages` holds the screens of the application shell. `AppRoutingModule` routes them directly: `start` to `v1-start-page`, `loginValidation` to `v1-login-validation-page`, `exceptionInfo` to `exception-information-page`, and `dashboard` to `dashboard-home-page`. `dashboard` is behind `TokenAuthorizationGuard`. The empty path redirects to `start`.

- `app/panels` holds panels used only by those core pages. They are not routes. The login validation page is built from `login-validation-progress` and `login-validation-exception`.

- A panel used on core pages and on other pages belongs in `modules/header`. It is declared and exported there, not in `app/panels`. `app-info-panel`, `server-info-panel`, and `v1-pilot-panel` follow that rule. A core page can host them. A section page can host them too: `v1-loyalty-recommendations-page` places `app-info-panel` and `server-info-panel` beside `v1-loyalty-corporation-selection-panel` and `v1-loyalty-offer-recommendations-panel`.

- Section modules follow the Infinity division. Industry is `modules/industry`, root path `industry`, pages in `modules/industry/pages`. Manufacture is `modules/industry/manufacture`, root path `industry/manufacture`, pages in `modules/industry/manufacture/pages`. Planetary is `modules/planetary`, root path `planetary`, pages in `modules/planetary/page`. Loyalty is `modules/loyalty`, root path `loyalty`, pages in `modules/loyalty/page`. Fittings is `modules/fittings`, pages in `modules/fittings/pages`, and it is not loaded from the root router. Industry and manufacture use the folder names `pages` and `panels`. Planetary and loyalty use `page` and `panel`. Industry also routes `app/industry/pages/v1-mining-operations-page` at `industry/mining/miningoperations`. Its render pieces sit in `app/industry/renders`, and `app/industry/panels` holds `v1-miningoperations-panel`.

- These modules supply pieces to pages. They do not represent an application section and they do not own a root route: `modules/header` holds shared header panels, `modules/shared` holds shared panels, renders, and the viewer, `modules/renders` holds render components for fittings, planetary, loyalty, and industry, `modules/common` holds pipes and small components such as `v1-feature-button`, and `modules/innovative-core` holds base components and services.

- New core screens go in `app/pages`. New panels used only by core pages go in `app/panels`. New panels used on core pages and on other pages go in `modules/header`. A screen that belongs to a section goes in that section module, with that section's panels beside it.

- A node is a renderable item. Its source data lives on a business object. That object usually has methods that shape the values for the UI, such as a display name, an icon URL, or a cost already scaled for the screen. The node does not read the raw source past those methods. The node, its Part, and its business object are the Model-View-Controller trio. The business object is the model. The render is the view, and one data source can have several variants. The Part is the controller and the main control for the node. Extra controllers may attach to the Part. They extend the same set of nodes sideways and do not add another level of children. The display reads the business object only through the methods the node exposes. The Part is the controller that chooses the render and calls those methods.

- The render draws one node. A listing variant shows few fields. Another variant can hold its own hierarchical nodes inside the same data source. `jsonClass` on the node picks which render component is used. The variant picks which layout of that render is used. `v1-blueprint-render` extends the node container and reads the node as the business object: blueprint name, output name, manufacture cost, output price, and cost index. The variant `-AVAILABLE-BLUEPRINTS-` is the detailed layout. Any other variant is the short layout. `v2-node-container` chooses this render when the node's `jsonClass` is `ProcessedBlueprintSummary` or `ProcessedBlueprint`, and it passes the same `variant` through.

- Nodes form a hierarchy. Rendering converts that hierarchy into a list, and the list is rebuilt when visibility or expansion changes. An invisible node does not contribute to the render list. A collapsed node contributes itself and does not contribute its children. An expanded node contributes itself and its visible children. `collaborate2View` is that conversion. `LookupRegion` returns only itself while it is collapsed, and returns its systems when it is expanded. `AppPanelComponent.notifyDataChanged` walks the root, calls `collaborate2View` with the current variant, and stores the result in `renderNodeList`. Expanding a node calls `toggleExpanded` and then `notifyDataChanged`, so the list is trimmed again immediately.

- A container panel owns the nodes it shows. It feeds the viewer `nodes2render` and a `variant`. The viewer walks that already flat list and gives each node to `v2-node-container` with the same variant, the panel as `downloader`, and `selectOnHover`. `modules/shared/core/viewer-panel` (selector `viewer-panel`) and `neocom-viewer-panel` both take that contract. The shared viewer uses `ChangeDetectionStrategy.OnPush` and numbers each row with `getNextIndex()`. The fitting contents panel and the blueprint BOM panel bind the viewer with `[nodes2render]="getNodes2Render()"` and `[variant]="getVariant()"`. The blueprint BOM panel is the viewer use case: `notifyDataChanged` builds the visible list, each row is a `v2-node-container`, and the display is one row per visible node.

- A standalone panel receives one node and one variant. There is no hierarchy and no viewer list. Its Part uses that pair to select the render and is the controller that reads the business object's data. The render does not fetch the model on its own. The sample is a blueprint panel given one `ProcessedBlueprint` and the variant `-AVAILABLE-BLUEPRINTS-`: the Part selects `v1-blueprint`, the render calls `getBlueprintName`, `getOutputName`, `getManufactureCost`, `getOutputPrice`, and the icon methods, and the display is that one detailed card. The same node with any other variant uses the short layout of the same render.
