# Node, render registry, and viewer

System: `front`. Feature: `node-render`.
OpenSpec change: `front-node-render` → `specs/front/node-render/spec.md`.

Source: `L2/02.EPIC-ANGULAR-CODIFICATION.nodes.md` (EPIC-002).

| ID | Status | Requirement |
| --- | --- | --- |
| NODE-001 | registered | A node is a renderable item. Its source data lives on a business object that shapes UI values (display name, icon URL, scaled cost). The node does not read the raw source past those methods. Node, Part, and business object are the MVC trio: business object = model; render = view (Angular component template); Part = controller that chooses the render and calls node methods. Extra controllers may attach to the Part sideways and do not add another level of children. |
| NODE-002 | registered | `jsonClass` on the node identifies which render to use; the variant picks which layout of that render is used. Hard-coded `*ngIf` branches in `v2-node-container` MUST be replaced by a render registry: each render registers which `jsonClass` values it accepts; at paint time look up the registry and place that render (`NgComponentOutlet` or `ViewContainerRef.createComponent`). No per-class branch in the container HTML. |
| NODE-003 | registered | Nodes form a hierarchy. Rendering converts that hierarchy into a list rebuilt when visibility or expansion changes. Invisible nodes do not contribute. Collapsed contributes itself only; expanded contributes itself and visible children. `collaborate2View` is that conversion. `AppPanelComponent.notifyDataChanged` walks the root, calls `collaborate2View` with the current variant, and stores the result in `renderNodeList`. Expanding calls `toggleExpanded` then `notifyDataChanged`. |
| NODE-004 | registered | A container panel owns the nodes it shows. It feeds the viewer `nodes2render` and a `variant`. When a page hosts `neocom-viewer-panel` (or `viewer-panel`), that viewer processes the flat list and places one node container per entry. Identification uses `jsonClass` via the render registry. Panels bind `[nodes2render]="getNodes2Render()"` and `[variant]="getVariant()"`. |
| NODE-005 | registered | Full render flow sample: `v1-blueprint-list-page` hosts `v1-available-blueprints-panel`; panel downloads `ProcessedBlueprint` nodes, `completeDowload` → `notifyDataChanged` → viewer; selection signals the page for BOM panel; expand/hide re-runs `notifyDataChanged`; the viewer never walks the hierarchy. |
| NODE-006 | registered | Rendering class structure — UI: page hosts feature panels; `BackgroundEnabledComponent` → `AppPanelComponent` (`IViewer`) → feature panel (`IRefreshable`) → `neocom-viewer-panel` → `V2NodeContainerRenderComponent` → feature render. Domain: `INode` / `ICollaboration` / `IExpandable` / `ISelectable` → `NeoCom` → `NeoComDelayed` → feature node. Panel owns roots; collaboration flattens; viewer loops; container resolves render by `jsonClass` (registry); render template is the row HTML. |
| NODE-007 | registered | A standalone panel receives one node and one variant. There is no hierarchy and no viewer list. Its Part uses that pair and the same registry lookup to select the render. The render does not fetch the model on its own. |
| NODE-008 | registered | Sample render: `v1-blueprint-render` extends the node container and reads the node as the business object. Variant `-AVAILABLE-BLUEPRINTS-` is the detailed layout; any other variant is the short layout. Registry maps `ProcessedBlueprintSummary` and `ProcessedBlueprint` to this render. |
| NODE-009 | registered | Viewer contract: `neocom-viewer-panel` and `modules/shared/core/viewer-panel` share inputs — `nodes2render` (`ICollaboration[]`), `downloader` (`AppPanelComponent`), `variant` (default `-DEFAULT-`), `selectOnHover`. The viewer iterates `getNodes2Render()` and places one `v2-node-container` per entry with `container`, `node`, `variant`, and `selectOnHover`. |
| NODE-010 | registered | Render registry: a registry service maps `jsonClass` → render component type. Registration happens when the render is declared (feature provide/bootstrap, or an explicit `register` call). At paint time the node container uses `NgComponentOutlet` or `ViewContainerRef.createComponent`, passes `container`, `node`, and `variant` as inputs. Shared attribute names across several `jsonClass` values mean registering the same render for each of those classes. |
| NODE-011 | registered | Relationships: the business object stays behind the node; the display never reads it except through methods the node exposes. The Part is the only controller that chooses the render and calls those methods. A second attached controller works on the same nodes beside the Part. `jsonClass` picks the render; the variant picks the layout; visibility and expansion decide whether the node is on the display list. |
| NODE-012 | registered | Standalone use case: a blueprint panel given one `ProcessedBlueprint` and variant `-AVAILABLE-BLUEPRINTS-` selects `v1-blueprint`; render calls node getters; detailed card. Any other variant uses the short layout. No hierarchy and no viewer list. |
| NODE-013 | registered | Viewer use case: before draw, `notifyDataChanged` turns the root into `nodes2render`. Invisible left out; collapsed only itself; expanded also visible children. The viewer does not walk the hierarchy; it walks the list it was given. |
| NODE-014 | registered | UI class roles: page hosts panels and receives selection signals; does not own `dataModelRoot` or the render list. `BackgroundEnabledComponent` holds backend `Subscription`s and cleans them on destroy. `AppPanelComponent` implements `IViewer`, owns `dataModelRoot`, `renderNodeList`, download flag, variant, and `SingleSelectionManager`. Feature panels extend it, often implement `IRefreshable`, download domain nodes, set variant, call `completeDowload`, host the viewer. Viewer panels are presentational. `V2NodeContainerRenderComponent` is the row shell; target is registry lookup only. Feature renders extend the node container and expose display helpers. |
| NODE-015 | registered | Domain node roles: `INode.getJsonClass()` for render identity; `ICollaboration.collaborate2View(...)` for flat contribution; `IExpandable` for expand/collapse; `ISelectable` for selection. `NeoCom` implements those four; default `collaborate2View` returns `[this]`. `NeoComDelayed` adds `ready` / `isReady()`. Feature nodes extend `NeoCom` or `NeoComDelayed`, set `jsonClass`, and add getters the render calls. |
| NODE-016 | registered | How layers connect: the panel is both `IViewer` and owner of node roots. Each root is an `ICollaboration`. Collaboration produces the flat `ICollaboration[]` the viewer receives. The viewer only loops that array. The node container receives one `NeoCom` and uses `jsonClass` to choose a render; the render subclass narrows the node type and binds template fields to node methods. |
| NODE-017 | registered | Blueprint list full render flow (manufacture sample): page hosts available-blueprints panel and optional BOM panel; panel sets variant, downloads, transforms to `ProcessedBlueprint`, `completeDowload` → `notifyDataChanged` → viewer → container registry resolve → render; selection/expand re-run the flat list path; viewer never walks the hierarchy. |
