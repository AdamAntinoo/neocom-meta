- SSE workflow summary (L1 detailed mermaid — behaviour only): front UI opens the viewer, asks the adapter, paints via `completeDowload` or merge, and may show delayed/partial rows until `notifyDataChanged` updates a row in place. Adapter: cache lookup → return cache or HTTP GET Nest → write/merge cache → open SSE `EventSource` for the list scope → on event merge node by id. Nest HTTP: list service → persistence lookup → return stored (then staleness check → maybe start background) or ESI → build simplified partial nodes → return partial + start background. Nest background: take next incomplete item → compute expensive fields → store full item in persistence → emit SSE updated node or patch → loop until idle. External: ESI CCP and the persistence database. After leave/return: cache hit with prior SSE enrichments for instant paint; reopen SSE; unfinished or stale items keep flowing.
  - Reason: restates FASSE-004/005 and BASSE-003/004 already registered.

- SSE phase summary: Phase 1 first paint — adapter cache or HTTP yields a partial or stored list, viewer shows rows, open SSE. Phase 2 enrichment — background next item → persist → SSE push → adapter merge → row refresh → next item. Phase 3 return visit — cache hit → instant paint → SSE again → stale refresh if needed.
  - Reason: restates FASSE-004/005 and BASSE-003/004 already registered.

- Async / SSE path requirements: opening a heavy page must not block until every node is fully computed — partial presentation is required. The front adapter is the single entry for list fetch: cache first, then Nest HTTP, then merge SSE into cache and UI. Backend persistence stores processed/expanded items and is distinct from the front cache; ESI when persistence has nothing yet. Expensive per-item work runs in a background process that completes items one by one, writes persistence, and emits SSE events. Updates after first paint change the existing UI in place — no page reload, route change, or leaving the screen. Stale persistence data is still returned immediately; refresh continues in the background with SSE updates. The same node → collaboration → viewer → registry → render pipeline is reused; async only changes how and when `dataModelRoot` (and node readiness) is updated. A delayed / not-ready node must be renderable in a safe partial state; when it becomes ready via SSE, the same row updates. SSE is the required server-to-client protocol for this epic (Nest `@Sse()` stream; front `EventSource` or equivalent authenticated stream consumer).
