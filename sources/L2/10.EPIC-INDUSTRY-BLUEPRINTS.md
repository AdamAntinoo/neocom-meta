## Section 10 — process blueprints into the location hierarchy

| ID | Status | Requirement |
| --- | --- | --- |
| IND-BP-110 | registered | On page start, the **v1-blueprint-by-location** page controller SHALL request the selected pilot’s industry blueprints from the NeoCom back (EPIC-007 Flow 06 / `GET /v1/pilots/{pilotId}/industry/blueprints`) |
| IND-BP-111 | registered | The blueprint list MAY arrive **partially** and MAY continue to be **fed over SSE** (EPIC-007 Flow 07 / `.../blueprints/events`); the front SHALL process blueprints **when available**, not only after a final complete list |
| IND-BP-112 | registered | While processing each available blueprint, the controller SHALL **aggregate** it as a **child of its System** node (create the System node if missing) |
| IND-BP-113 | registered | System nodes SHALL be **aggregated as children of their Region** nodes (create the Region node if missing) |
| IND-BP-114 | registered | The host panel’s root nodes for rendering SHALL be the aggregated **Region** nodes (hierarchy Region → System → Blueprint per Section 04) |
| IND-BP-115 | registered | Region and System child counts used by **`v1-region-render`** / **`v1-system-render`** SHALL follow the aggregated children |
| IND-BP-116 | registered | After aggregation changes (including SSE updates), the panel SHALL rebuild the render list so expanded/collapsed views stay consistent with the tree (EPIC-002 `notifyDataChanged`) |
| IND-BP-117 | registered | Grouping uses each blueprint’s **location chain** (system → region); the front does not invent regions/systems without a blueprint that maps to them |
| IND-BP-118 | registered | Front SHALL NOT call ESI to obtain the pilot blueprint list or to build the hierarchy — NeoCom back / SSE supply the blueprint feed |
