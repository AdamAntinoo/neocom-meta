## Goals

The current `blueprint-by-location-panel` implementation should return to the design table because the implementation does not fit with the expected implementation related to the use of models and ther helper classes. This epic details a correct implementation that may deprecate some of the current applied specs.

**Interchange vs front domain:** published domain classes **no longer belong to** `neocom-domain` for this flow. The backend defines its own **interchange** classes on `**neocom-back`**, named with the** `**Dto` **suffix** (e.g. `BlueprintV1Dto`, `SpaceLocationV1Dto`). The front maps those DTOs into `**neocom-front` `NeoCom` node** classes for processing and render.

## Section 01 — Pilot blueprint feed into `blueprint-by-location-panel`

### Scope

Processing of **pilot blueprints** so they can be **rendered** on the `blueprint-by-location-panel` (`neocom-front` industry manufacture panel). This epic redesigns that processing around **models and helper classes**; parts of EPIC-010 Section 10 / applied `front-industry-blueprints` MAY be deprecated when this design lands.

### Process start — local provider

The process SHALL **start** by retrieving the pilot’s blueprints from a **local provider**. That local provider SHALL implement the **SSE management** of the pilot blueprints (subscribe / deliver updates for the selected pilot’s blueprint feed). The panel consumes blueprints from that provider for rendering; it does not own the SSE lifecycle itself.

#### Placement and name

The local provider SHALL live in the front `**services` module** (`neocom-front` `src/app/modules/services/`) so it is **available to all panels**, not only `blueprint-by-location-panel`. The Angular artefact SHALL use a **significant** name and the `**.service`** suffix.

Programme name: `**PilotBlueprintProviderService**`  
File: `modules/services/pilot-blueprint-provider.service.ts`

#### Cache, expiry, and merge

The local provider SHALL be able to **cache** elements received from the SSE feed. Cached items SHALL be **tied to the pilot** (cache key includes the pilot identity) so **more than one pilot’s blueprint list can coexist** in the cache at once, each with its **own expiration time**. When a given pilot’s **cache expires**, the provider SHALL be able to **initiate a new retrieval** for **that pilot** without clearing other pilots’ entries. Retrieved elements carry **unique identifiers on the** `id` **attribute**, so **merging** new data with already-cached data for that pilot SHALL be **straightforward** (upsert / replace by `id`).

**Expiration duration** for the pilot blueprint list follows the **ESI** cache window for [Get character blueprints](https://developers.eveonline.com/api-explorer#/operations/GetCharactersCharacterIdBlueprints) (`GET /characters/{character_id}/blueprints/`): **60 minutes**. Per-pilot cache entries SHALL use that **60-minute** TTL (unless ESI later publishes a different window for the same operation — then follow ESI).

#### Domain model shape

Elements exposed by the local provider (cached, retrieved, or merged) SHALL **always** be `**neocom-front` domain models that inherit from `NeoCom`** — not raw wire DTOs alone. Blueprint leaves use `**BlueprintNodeV1`**; Region / System nodes follow Section 02. Wire interchange from the back uses** `**Dto`**-suffixed** classes (Section 03).

### Sort and hand-off to node rendering

After aggregation, the processing SHALL **sort the Region roots by name**, then **provide those Region nodes** to the **node-rendering** path (panel `nodes2render` / collaborate — EPIC-002; EPIC-010 **IND-BP-116** rebuild after updates).

### Front domain nodes (`NeoCom` subclasses)

On `neocom-front`, hierarchy levels for this panel SHALL be **new domain node classes** that **inherit from** `NeoCom` (`innovative-core/domain/NeoCom.ts` — front render/node base). They are **not** `neocom-domain` types and are **not** back interchange DTOs.

| Level            | Class                                                     | Base             |
| ---------------- | --------------------------------------------------------- | ---------------- |
| Blueprint (leaf) | `**BlueprintNodeV1**`                                     | extends `NeoCom` |
| Region (root)    | new `NeoCom` subclass (same pattern as `BlueprintNodeV1`) | extends `NeoCom` |
| System (middle)  | new `NeoCom` subclass (same pattern as `BlueprintNodeV1`) | extends `NeoCom` |

These replace ad-hoc aggregation holders that do not fit the models / helper design (epic Goals). Exact Region / System class names stay as named when authored; until then they remain “new `NeoCom` subclasses parallel to `BlueprintNodeV1`”. Back → front wire uses `**neocom-back` `*Dto` classes** (e.g. `**BlueprintV1Dto`**); front nodes wrap / map those DTOs for collaborate / expand / select.

## Section 03 — Blueprint location: catalog → `SpaceLocationV1Dto` → `SpaceLocationNodeV1`

### Back — ESI contents → `neocom-back` `BlueprintV1Dto`

Backend blueprint **data contents** are obtained from the **ESI API**, for example:

```json
{
  "item_id": 1009214402302,
  "location_flag": "Hangar",
  "location_id": 60006907,
  "material_efficiency": 10,
  "quantity": -1,
  "runs": -1,
  "time_efficiency": 20,
  "type_id": 31683
}
```

That ESI payload SHALL be **transformed** into the `**neocom-back` interchange class `BlueprintV1Dto`** (`Dto` suffix; defined on `**neocom-back`**, not `neocom-domain`). Field family aligns with former EPIC-004 [§10 BlueprintV1](./04.EPIC-MODELS.md#section-10--blueprintv1) intent, under Dto naming for this epic.

Pilot blueprints from the back **carry location information** (at least `location_id` / `location_flag` from ESI). During **backend processing**, that location SHALL be **obtained via the existing space-location use case** (catalog lookup logic stays in **one** place — not reimplemented or catalog-called from every consumer) and represented as `**SpaceLocationV1Dto`** on `neocom-back` (Dto suffix; EPIC-004 [§20 SpaceLocationV1](./04.EPIC-MODELS.md#section-20--spacelocationv1) / EPIC-008 catalog contracts as the location semantics source, e.g. **LOC-001** / **LOC-002** / **LOC-010**). The `**BlueprintV1Dto` class SHALL also contain the instance of that `SpaceLocationV1Dto`** derived from that use-case result.

**Use-case composition (back):** a use case MAY **call other use cases** to obtain additional information so shared behaviour lives in a **single** place and is **not copied** at every call site (example: pilot-blueprints use case → space-location use case for each blueprint `location_id`).

**DTO converters (back):** origin→DTO mappings for this flow SHALL be **aggregated into a single converter class** under `neocom-back` `infrastructure/adapters/dto` (multiple conversion **methods** inside that class, not one class per mapping). That converter class SHALL be **static** — call sites use static methods; it SHALL **not** be instantiated.

### Front

On reception, that `SpaceLocationV1Dto` SHALL be **transformed** into a local `neocom-front` domain class `**SpaceLocationNodeV1`** that **inherits from** `NeoCom`, and SHALL be **tied to the blueprint** (`BlueprintNodeV1`). Processing SHALL then **extract the region and system identifiers** from that tied location node for **aggregation** (Section 02; EPIC-010 **IND-BP-117** location chain).

## Section 04 — Real-time provider → panel integration (design)

### Problem

`PilotBlueprintProviderService` owns SSE + cache (BLP-002, BLP-010…012). The **representation panel** (`blueprint-by-location-panel`) must **aggregate** and **paint** Region → System → Blueprint (Section 02) while the feed is still live (EPIC-010 **IND-BP-111**, **IND-BP-116**). Today panels subscribe to SSE themselves via `NodeListAdapterService.openEnrichment` and merge locally — that **duplicates** SSE lifecycle and fights the “provider owns SSE” rule (Section 01).

The connection from provider to panel MUST support **real-time updates** of retrieved data without each panel opening its own SSE.

### How to solve it (selected: approach A)

**Selected approach — A:** a **shared** `Observable` from `PilotBlueprintProviderService`, multicasted with `**shareReplay` (and/or `refCount`)**, emitting** `**NeoCom[]` **snapshots and/or upsert events** (always `NeoCom` / `BlueprintNodeV1` — BLP-013).

Keep **one** SSE + cache owner (`PilotBlueprintProviderService`). Panels **subscribe** to that shared Observable; they do **not** call `AuthenticatedSseClient` directly. `shareReplay` lets late subscribers receive the latest snapshot; `refCount` (or equivalent) ties SSE lifetime to active subscribers.

On each emission the panel:

1. Merges into its working set by `id` (or replaces from a full snapshot when cache refresh / expiry retrieval completes — BLP-011).
2. Re-runs aggregation + Region name sort (Section 02).
3. Calls `AppPanel.completeDowload` / `notifyDataChanged` so `collaborate2View` rebuilds `renderNodeList` (EPIC-002; current `app-panel.component.ts`).

```mermaid
sequenceDiagram
  participant Panel as blueprint-by-location-panel
  participant Prov as PilotBlueprintProviderService
  participant SSE as AuthenticatedSseClient
  participant Back as neocom-back SSE

  Panel->>Prov: observeBlueprints(pilotId) — shared Observable (shareReplay / refCount)
  Prov->>Prov: read cache → emit NeoCom[] / upsert
  Prov->>SSE: open events (once per pilot scope while refCount > 0)
  SSE->>Back: GET .../blueprints/events
  loop node-updated
    Back-->>SSE: BlueprintV1Dto (+ SpaceLocationV1Dto)
    SSE-->>Prov: event
    Prov->>Prov: map DTO→NeoCom; upsert cache by id; next(shared Observable)
    Prov-->>Panel: NeoCom[] snapshot or upsert event
    Panel->>Panel: aggregate + sort Regions
    Panel->>Panel: notifyDataChanged
  end
  Panel-->>Prov: unsubscribe (panel destroy)
  Note over Prov: refCount — close SSE when last subscriber leaves
```

**Rejected alternatives (do not use for this integration):**

| Approach | Verdict |
| --- | --- |
| B. Panel polls the provider cache on a timer | Reject — not real-time |
| C. Panel keeps its own SSE beside the provider | Reject — duplicates BLP-002 |
| D. Angular signals / `resource` only | Reject for this contract — approach **A** is normative; signals MAY wrap the Observable later without replacing it |

Reference patterns already in tree: `NodeListAdapterService` (cache + Observables), `AuthenticatedSseClient`, panel subscribe + `notifyDataChanged` (FASSE-005).

### Impacts

| Area                                 | Impact                                                                                                                                            |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Panels**                           | `blueprint-by-location-panel` (and any other consumer) become thin: subscribe → aggregate → render. SSE moves out of the panel.                   |
| **Shared service**                   | Single feed per pilot scope; second panel gets the same stream without a second SSE.                                                              |
| **EPIC-010 §10**                     | Load path shifts from “page/panel opens SSE” to “provider opens SSE” (Section 01); aggregation / `notifyDataChanged` rules stay (IND-BP-112…116). |
| **FASSE /** `NodeListAdapterService` | Likely superseded or narrowed for industry blueprints; migration cost on `available-blueprints-panel` if it should share the same provider.       |
| **Expand / selection UX**            | Full `notifyDataChanged` rebuild on every upsert is correct but may reset scroll focus unless helpers preserve expanded `id`s — see risks.        |
| **Testing**                          | Provider stream can be mocked with RxJS; less need to fake EventSource in every panel test.                                                       |

### Risks

| Risk                                                                  | Mitigation                                                                                                                                       |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **High-frequency SSE** floods aggregation / UI                        | Debounce or coalesce upserts (e.g. `auditTime` / batch by animation frame) inside provider or panel — exact policy TBD; do not invent a rate yet |
| **Expand/selection lost** on rebuild                                  | Preserve expanded / selected node `id`s across `notifyDataChanged`                                                                               |
| **Duplicate SSE** if any panel still opens enrichment                 | Lint / code review: only provider uses `AuthenticatedSseClient` for this feed                                                                    |
| **Cache expiry mid-view** triggers full re-fetch while SSE still open | Define ordering: snapshot replace vs merge; emit one clear “reset” then upserts (BLP-011)                                                        |
| **Memory / orphan SSE** when navigating away                          | Prefer `**refCount`** on the shared Observable so SSE closes when the last subscriber unsubscribes; test multi-panel subscribe/unsubscribe       |
| **Location missing** on early SSE events                              | Partial `SpaceLocationNodeV1`; aggregation skips or parks until location present (IND-BP-117) — behaviour TBD if not specified                   |
| **Dto ↔ NeoCom drift**                                                | Single map function in the provider; panels never parse DTO JSON                                                                                 |
