## Section 01 — Domain as truth repository

First backend implementation tip for correct `neocom-back` services.

**Purpose:** Establish where programme domain elements for backend services live.

**`neocom-domain` is the truth repository** for domain elements. That includes:

- **Interchange classes** between the back and the front (domain models on the shared contract).
- **Port interfaces** — interface definitions for the service API implementations (known as ports).

### Placement

| Kind | Location in `neocom-domain` |
| --- | --- |
| Interchange models | `src/domain` |
| Port interfaces | `src/ports` |

All ports SHALL be created under `neocom-domain` `src/ports`. All interchange models SHALL be created under `neocom-domain` `src/domain`. Further classification (if it applies) will be determined later.

| ID | Review | Requirement |
| --- | --- | --- |
| BACK-SVC-001 | extracted | `neocom-domain` SHALL be the truth repository for domain elements used by backend services: interchange classes between back and front, and port interfaces for service API implementations |
| BACK-SVC-002 | extracted | Interchange models SHALL be created under `neocom-domain` `src/domain` |
| BACK-SVC-003 | extracted | Port interfaces SHALL be created under `neocom-domain` `src/ports` |
| BACK-SVC-004 | extracted | Further classification of contents under `src/domain` / `src/ports` MAY be determined later; until then use only that split |

## Section 02 — Existing domain classes: place, Record base, version suffix

Second backend implementation tip for correct `neocom-back` / `neocom-domain` alignment.

**Purpose:** Bring already-implemented domain classes into the truth layout from Section 01, on a shared base type, with versioned type names.

### Move to the right place

Already implemented domain / interchange classes SHALL be moved (or kept) under `neocom-domain` `src/domain` as required by BACK-SVC-002. Ports stay under `src/ports` (BACK-SVC-003). Do not leave interchange models only under ad-hoc folders (e.g. legacy `src/dto` or back-local domain copies) when they are programme interchange types.

### Inherit from Record

Domain interchange classes SHALL inherit from the `Record` base in `neocom-domain` `src/interfaces/Record.interface.ts` (`Record` provides `jsonClass` and field assign construction).

### Version suffix (type names)

Implementation / published type names SHALL use a **version suffix** (e.g. `…V1`, `…V2`), not an unversioned bare name.

**Initially copied classes** (first copies into the truth repository for a given model) SHALL start at **V1** (suffix `V1`).

| ID | Review | Requirement |
| --- | --- | --- |
| BACK-SVC-010 | extracted | Already implemented domain interchange classes SHALL be placed under `neocom-domain` `src/domain` (the interchange home from Section 01) |
| BACK-SVC-011 | extracted | Those domain interchange classes SHALL inherit from `Record` (`neocom-domain` `src/interfaces/Record.interface.ts`) |
| BACK-SVC-012 | extracted | Implementation type names for those classes SHALL use a version suffix (e.g. `BlueprintV1`), not an unversioned bare name |
| BACK-SVC-013 | extracted | Initially copied classes SHALL start at version **V1** (name suffix `V1`) |

## Section 03 — Ports: keep Pilot, Industry for other endpoints

Third backend implementation tip: organise existing and new **ports** under `neocom-domain` `src/ports` (BACK-SVC-003).

**Purpose:** Keep a dedicated Pilot port; put other (non-pilot) service endpoints behind an Industry port in the domain truth place.

### Existing ports

There are already port-shaped contracts in use (e.g. back `PilotSource`; domain legacy `IndustryServiceInterface` under `src/api/`). Those SHALL be **created or moved** into `neocom-domain` `src/ports` rather than remaining only as back-local application ports or under `src/api/`.

### Pilot port — keep

The **Pilot** port SHALL be **kept** as its own port (pilot find / pilot data access). Move it to `neocom-domain` `src/ports` if it still lives only under `neocom-back`. Do not fold Pilot into Industry.

### Industry port — other endpoints

Other endpoints (non-pilot service APIs in this epic’s backend-services scope — e.g. blueprints, fittings, mining operations, and related industry item access) SHALL be available under a **new Industry port**, either:

- **created** as a new port interface under `neocom-domain` `src/ports`, or  
- **moved** there from an existing industry-shaped interface (e.g. legacy `src/api/IndustryServiceInterface`) and extended as needed.

| ID | Review | Requirement |
| --- | --- | --- |
| BACK-SVC-020 | extracted | Existing ports SHALL be created or moved under `neocom-domain` `src/ports` (domain truth place for ports) |
| BACK-SVC-021 | extracted | The Pilot port SHALL be kept as a separate port (not merged into Industry) and live under `neocom-domain` `src/ports` |
| BACK-SVC-022 | extracted | Non-pilot service endpoints in this epic’s scope SHALL be exposed through an Industry port under `neocom-domain` `src/ports` (create new or move/extend an existing industry interface) |

## Section 04 — Port contracts: back implements, domain models only

Fourth backend implementation tip: what a port is, who implements it, and which types it may use.

**Purpose:** Bind ports to use cases and restrict port signatures to published domain models.

### Role

Ports are **interfaces**. They SHALL be **implemented by back services** (adapters in `neocom-back`). Use cases SHALL depend on those ports (injected), not on concrete adapters.

### Models on ports

Types used on port method signatures (parameters and return types) SHALL be **exclusively** models available from `neocom-domain` (interchange / domain types under the truth repository — typically `src/domain`).

If a required model is **missing** from `neocom-domain`, agents and implementers SHALL **stop** and **request more information**. Do not invent a local or back-only model to fill the gap; do not invent a domain type that the programme has not defined.

| ID | Review | Requirement |
| --- | --- | --- |
| BACK-SVC-030 | extracted | Ports SHALL be interfaces implemented by `neocom-back` services (adapters) and consumed by use cases |
| BACK-SVC-031 | extracted | Port signatures SHALL use exclusively models available in `neocom-domain` |
| BACK-SVC-032 | extracted | When a model needed by a port is missing from `neocom-domain`, work SHALL stop and more information SHALL be requested (no invented substitute type) |

## Section 05 — Domain DTOs deprecated

Fifth backend implementation tip: legacy DTO types under `neocom-domain`.

**Purpose:** Mark existing domain DTOs so call sites are easy to spot; keep the sources for later template use or removal — not as active interchange or port contracts.

Domain DTOs (e.g. under `neocom-domain` `src/dto/`) are **deprecated**. They SHALL be marked as deprecated in code (TypeScript `@deprecated` / JSDoc `@deprecated` or equivalent) so uses are easy to identify. They SHALL be **kept** for now as templates or for later removal — not deleted in this pass, and not used as the truth interchange models (`src/domain`) or port types (`src/ports`).

| ID | Review | Requirement |

| BACK-SVC-041 | extracted | Domain DTOs SHALL be marked deprecated in code so call sites are easy to identify |
| BACK-SVC-042 | extracted | Deprecated domain DTOs SHALL be kept for later use as templates or for removal (not deleted solely by this requirement) |

## Section 06 — Domain `esi-api` deprecated (ESI stays in back)

Sixth backend implementation tip: ESI-shaped types must not leave the back via the domain package.

**Purpose:** Deprecate and allow removal of `neocom-domain` `src/esi-api` so ESI API DTOs / class data are not exported outside `neocom-back`.

`neocom-domain` `src/esi-api` is **deprecated**. ESI DTOs and class data from the ESI API SHALL **not** be exported outside the back. Therefore that tree MAY be **removed** from `neocom-domain` (ESI access and ESI-shaped types stay inside `neocom-back`). Mark the package contents deprecated for easy identification until removal.

| ID | Review | Requirement |
| --- | --- | --- |
| BACK-SVC-050 | extracted | `neocom-domain` `src/esi-api` SHALL be treated as deprecated |
| BACK-SVC-051 | extracted | ESI DTOs and ESI API class data SHALL NOT be exported outside `neocom-back` via `neocom-domain` |
| BACK-SVC-052 | extracted | `neocom-domain` `src/esi-api` MAY be removed from the domain package (ESI types remain back-internal) |

## Section 07 — OpenAPI first; schemas follow domain; model wins

Seventh backend implementation tip: first stage of new back code when a port is updated.

**Purpose:** Start from OpenAPI when applicable; align schema and path naming with domain; resolve conflicts in favour of the domain model.

### First development stage

For new `neocom-back` code, the **first development stage** SHALL be to **update the OpenAPI specification** for the **port being updated**, **when OpenAPI applies** to that port / endpoint surface. Do not skip OpenAPI update when the change exposes or changes an HTTP contract for that port.

### Schema and path naming

- OpenAPI **schemas** SHALL be named after their **domain model names** (programme type names from `neocom-domain`).
- Endpoints SHALL be **versioned with a prefix** (e.g. path segment `v1`).

### Precedence

If there are **differences** between OpenAPI and the domain model (fields or names), the **domain model takes precedence** and **supersedes** the OpenAPI document. Align OpenAPI to the model; do not change the model to match a divergent OpenAPI schema.

| ID | Review | Requirement |
| --- | --- | --- |
| BACK-SVC-060 | extracted | The first development stage for new back code SHALL update the OpenAPI specification for the port being updated when OpenAPI applies |
| BACK-SVC-061 | extracted | OpenAPI schemas SHALL be named after their domain model names |
| BACK-SVC-062 | extracted | Endpoints SHALL be versioned with a path prefix (e.g. `v1`) |
| BACK-SVC-063 | extracted | When OpenAPI and domain model fields or names differ, the domain model SHALL take precedence and supersede the OpenAPI |

## Section 08 — Industry API: pilot blueprints (`BlueprintV1`)

First surface of the **new Industry API** / Industry port (Section 03). **To be reviewed.**

**Purpose:** Start Industry with the endpoint that returns blueprints belonging to a pilot.

### Endpoint

- **Input:** the pilot’s unique identifier (`pilotId`).
- **Result:** a **list** of **`BlueprintV1`** (domain interchange model; OpenAPI schema named `BlueprintV1` per Section 07).
- Path SHALL use a **version prefix** (Section 07). Exact path shape is subject to review (related inventory in EPIC-007 Flow 06 may inform; this epic owns the Industry-port contract).

Development SHALL start by updating OpenAPI for this Industry port surface when applicable (BACK-SVC-060).

### Mapping (subject to review)

Each list element SHALL be a `BlueprintV1` that:

1. Maps **all fields available** on the ESI character blueprints API response into the corresponding `BlueprintV1` / programme fields, and  
2. Includes the fields **already defined on `BlueprintV1`** that are **not** present on the ESI API payload (e.g. resolved names and icon URLs such as `blueprintTypeName`, `blueprintTypeIconURL`, `outputTypeId`, `outputTypeName`, `outputTypeIconURL`, and any other `BlueprintV1` fields beyond raw ESI), filled by back processing as defined for that model.

Exact ESI↔`BlueprintV1` field pairing **will be reviewed**. If a required domain field or ESI mapping is unclear or a model is missing, stop and request more information (BACK-SVC-032). Domain model fields take precedence over OpenAPI (BACK-SVC-063).

| ID | Review | Requirement |
| --- | --- | --- |
| BACK-SVC-070 | extracted | The new Industry API SHALL start with an endpoint that retrieves the blueprints belonging to a pilot |
| BACK-SVC-071 | extracted | That endpoint SHALL take the pilot unique identifier as input and return a list of `BlueprintV1` |
| BACK-SVC-072 | extracted | Each `BlueprintV1` SHALL map all fields available from the ESI blueprints API plus the `BlueprintV1` fields not present on ESI (names, icons, output type, and other model-only fields), with the detailed field mapping to be reviewed |
