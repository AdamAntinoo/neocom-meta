## Section 01 — Cypress UI and content validation

Testing is a most important part of the development process. This project will use SDD→BDD→TDD design model so from spec we should create gherkin scenarios that should be validated before the feature is completed. The gherkin will be done with the cypress tool that should validate flows and also the UI validity of the pages and panels found.

**Programme scope (front and back):** CICD-F-001’s SDD→BDD→TDD / Gherkin gate is mirrored on the back via [Section 06](#section-06--backend-testing) (`CICD-B-001…007`). Front uses Cypress + Gherkin for UI; back uses Gherkin feature files (Cucumber or equivalent) for API / OpenAPI behaviour. Both sides SHALL keep a **small, reusable step catalog** ([Section 10](#section-10--gherkin-step-catalogs-front-and-back)).

Cypress testing SHALL validate not only navigation flows but also the **contents** of panels and items and their **UI aspects**. That includes colour and other visual or structural properties that the application publishes for tests through the documented `cy-`* attributes (for example `cy-section-name`, `cy-field-value`, `cy-field-label`, `cy-name`, and any further catalogued Cypress properties).

Gherkin scenarios that cover a page or panel SHALL assert against those published properties so content and UI validity are checked with stable selectors before the feature is considered complete. Pages and panels under test SHALL expose the relevant `cy-*` properties so Cypress can locate and verify them.

| ID         | Review       | Requirement                                                                                                                                                                                                                                            |
| ---------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| CICD-F-001 | `registered` | `neocom-front` SHALL follow an SDD→BDD→TDD design model: from spec, create Gherkin scenarios that SHALL be validated before the feature is considered complete → `front-cicd` (was BDD-001)                                                            |
| CICD-F-002 | `registered` | Cypress SHALL validate navigation flows and also the **contents** of panels and items and their **UI aspects**, including colour and other visual or structural properties published through documented `cy-`* attributes → `front-cicd` (was BDD-002) |
| CICD-F-003 | `registered` | Gherkin scenarios that cover a page or panel SHALL assert against those published properties so content and UI validity are checked with stable selectors → `front-cicd` (was BDD-003)                                                                 |

## Section 02 — Mock data from real runs

For **automated** testing the system should provide mocked scenarios and configurations that allow to test the elements with predefined and stable data so adapters should be configurable and replaceable on the **automated** testing environment.

**Scope boundary:** captured / mock fixtures from real runs are **only** for automated Gherkin (and related automated suites). They SHALL **never** be used as the data feed for **development user testing** (manual exploratory / interactive use of the running app during development).

**Data feed for Gherkin:** test payloads SHALL be obtained from **back real endpoint results** (responses from the Nest / programme API under a real or controlled capture run). That captured response data is what Gherkin scenarios use as valid values for automated checks (including error, stale, and incorrect shapes when those were observed on the wire). The **authoritative store** of those payloads is the back **test mock data catalog** ([Section 06 — Sample outputs and mock catalog](#sample-outputs-and-mock-catalog-source-of-truth)).

## Section 03 — Coverage control and quality gates

The project SHALL provide a **tool to measure and control code testing coverage**. Coverage results SHALL be available to developers locally and in CI so gaps can be found before a feature is completed.

The project SHALL define **quality-gate rules** that use coverage (and related test outcomes) to pass or fail a change. A feature SHALL NOT be considered complete when required gates fail. Gate thresholds and which suites they apply to (unit, acceptance/Cypress, and any later layers) SHALL be recorded so agents and CI enforce the same rules.

NEOCOM projects SHALL **report to SonarCloud** so coverage, quality gates, and other quality findings are checked in one place. CI SHALL upload analysis (and coverage where applicable) to SonarCloud; a change that fails the configured SonarCloud quality gate SHALL NOT be considered complete.

Programme rules apply on **both** repos; each OpenSpec set carries its own ids.

## Section 05 — Testing command catalog

There SHALL be a **catalog of stable, common testing commands** shared across NEOCOM projects. Names SHALL be **short and clear**. Front and back MAY differ in how each command is implemented, but the catalog names and intent SHALL stay the same so agents and developers use one vocabulary.

The catalog SHALL cover separately:

| Layer   | Intent                                                     | Tooling (current)                                                                                                                      |
| ------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **TDD** | Unit testing                                               | Project unit runner (e.g. Vitest on front, Vitest on back)                                                                             |
| **BDD** | Acceptance testing                                         | Cypress with Gherkin (front); Gherkin/Cucumber (back)                                                                                  |
| **SDD** | Full integration testing on the **development deployment** | Gherkin feature files (beyond acceptance); initially **one feature file per page**; Cypress (or equivalent) against the deployed stack |

**SDD (beyond BDD acceptance):** SDD SHALL cover **cross-cutting automated UI / full integration tests** against the **development deployment** (not unit or isolated acceptance alone). Test guidance SHALL be written as **Gherkin feature files**. **Initially**, there SHALL be **one Gherkin feature file per page**.

Each catalog entry SHALL include the **environment setup** required to run that layer. There SHALL also be a command that runs **all testing layers in sequence** (TDD, then BDD, then SDD when defined), after applying the setup each layer needs.

## Section 06 — Backend testing

`neocom-back` SHALL follow the **same testing guidelines** as the front (SDD→BDD→TDD, coverage and quality gates, SonarCloud, shared command catalog intent, mock fixtures from real runs where applicable for automated testing only).

Backend acceptance and integration scenarios that need **stable, predefined data** SHALL use **mocked sources**, with **WireMock** (or an equivalent HTTP mock) replacing upstream dependencies for those scenarios. **Universe ESI** reference data MAY use **real ESI feeds** when that is acceptable for the scenario. Every other external source SHALL be decided **case by case** (mock vs live), and the choice SHALL be recorded for that scenario.

Backend BDD acceptance tests SHALL use **Gherkin** with **Cucumber** (or another BDD runner that consumes the same Gherkin scenarios) so acceptance behaviour is expressed the same way as Cypress-driven front acceptance.

### OpenAPI Gherkin feature files

Extending SDD→BDD→TDD to the back: there SHALL be **Gherkin feature files** (similar in role to front Cypress feature files) that **test the OpenAPI specifications**.

**Preferred — scenario-supplied test data:** OpenAPI Gherkin scenarios SHALL **define the test data on the scenario** (Examples tables, Doc Strings, or bound steps). That data MAY be **loaded into caches by the scenario** so each check is tied to **specific requests** and every case under test is visible in the feature file. Prefer this over opaque external fixtures so developers can see and control the data that drives each case.

**When stored mocks are better:** if defining the full payload **inside the scenario is complex**, scenarios SHALL use the [mock catalog](#sample-outputs-and-mock-catalog-source-of-truth) — selecting the **original** or **trimmed** stored set (CICD-B-015…017) — so the testing process stays simpler while the scenario still names which catalog entry/set applies.

**Alternative — ESI API mock (WireMock):** scenarios MAY obtain test data via an **ESI API mock** (WireMock or equivalent). When WireMock is used for this, each scenario’s expected upstream responses SHALL be **tied to that scenario**, selected with **additional request headers** that choose the correct stub response for every case. Relying on WireMock alone without scenario-visible data reduces developer visibility of what the test asserts — prefer scenario-supplied data when practical.

**Alternative — real ESI:** scenarios MAY use **real ESI API** results by selecting a **pilot** (or character) whose data set is **valid, traceable, and treated as static** for the scenario’s assertions. Record that choice on the scenario (per CICD-B-003 / CICD-B-004).

### Sample outputs and mock catalog (source of truth)

When **OpenAPI** definitions and the matching **endpoint implementations** are committed with `**/git:commit`**, `neocom-back` SHALL **generate sample outputs** suitable for automated testing and place/update them in a **catalog of test mock data**. That catalog SHALL remain **always ready** and is the **source of truth** for Gherkin (front and back) fixture selection described in [Section 02](#section-02--mock-data-from-real-runs).

**Trim for testing:** when back test data is built for testing purposes, each type MAY be reduced to **2 samples**; the rest SHALL be removed from the trimmed set. The **trimmed** mock data SHALL be **stored alongside the original** full capture so scenarios can **select** which set (original or trimmed) to use during testing.

### Versioning and image / artifact naming (implementation contract)

**Reference sample (pattern only):** workspace repo `smartydevops-reusable-workflows-cecabank-pagos/.github` — especially `actions/gitversion`, `actions/publish`, `actions/deploy-github-image`, `actions/calculate-image-tag`, `actions/pull-github-image`, and `workflows/publish-microservice-github.yml`. NEOCOM SHALL re-implement equivalent behaviour as **reusable actions/workflows in** `neocom-meta` (Node/Nest/Angular stack). Do **not** copy Cecabank Maven, GCP, or their secret names.

**SemVer bump and release (front / back apps):** GitVersion `MajorMinorPatch` SHALL follow these programme rules (hooks / CI / release process — do not hand-edit SemVer in `package.json`). Product `GitVersion.yml` SHALL set `tag-prefix: v` so release tags are `vX.Y.Z`.

| Event | Version effect |
| ----- | -------------- |
| Merge into `develop` completes | Increment **patch** (`X.Y.Z` → `X.Y.(Z+1)`) |
| Merge into `main` completes (default path: not a named `release/X.Y.Z` promotion) | Increment **minor** and reset patch (`X.Y.Z` → `X.(Y+1).0`) |
| Merge into `main` completes (any path) | Create an annotated **git tag** `v` + resulting `MajorMinorPatch` (e.g. `v0.5.0`) on that merge commit |

**Named release (explicit version):** when the developer runs a release that pins a version (e.g. `/release 1.0.0` → branch `release/1.0.0`):

1. Create the release branch **from** `main`.
2. Merge `develop` (with the changes to ship) **into that release branch**.
3. Do **not** apply the branch-named version (`1.0.0`) while work remains only on the release branch.
4. When the release merges to `main`, set the version to the `**X.Y.Z` from the release branch name** (not a default minor bump) and create the corresponding git tag `vX.Y.Z`.

Major bumps remain an explicit programme decision (not implied by every main merge).

**One naming scheme for feature (and other non-**`main`**) commits and artifacts:** versioning for commits applied on a branch SHALL use the same SemVer-derived string that names the published artifact / Docker image for that build. There is **no** separate “feature SemVer” vs “image tag” form — `commitTag` (package / app version written for that commit) and `imageTag` are the **same** string on every branch except `main` / `master`, where both publish as plain `majorMinorPatch`. Image naming SHALL **not** use a separate branch **channel** segment.

**GitVersion outputs the workflow SHALL compute** (meta reusable action `gitversion`):

| Output | Rule |
| ------ | ---- |
| `majorMinorPatch` | From GitVersion after the bump rules above (e.g. `0.4.0`) — numeric SemVer only; git tags add the `v` prefix |
| `imageTag` | On `main` / `master`: `majorMinorPatch` only. On every other branch: `{majorMinorPatch}{preReleaseLabelWithDash}.{shortSha}` (lowercase; `+` → `-`). Example: `0.4.0-feature-cicd.230d68bf` |
| `commitTag` (published package / app version for the commit) | **Identical** to `imageTag` on all branches — on `main` / `master` that is plain `majorMinorPatch`; elsewhere the prerelease form above |
| `appVersion` (optional deploy label) | Same base string as `imageTag`, then `+` → `.` and `.` → `_` (infrastructure-friendly label) |

**Image and registry names:**

| Kind | Form |
| ---- | ---- |
| Local build tag | `{artifactName}:{imageTag}` |
| GHCR repository | `ghcr.io/{github.repository_owner}/{artifactName}` |
| GHCR tags to push | `:{imageTag}` and `:latest` |
| `artifactName` | Short service/image name committed in the product caller workflow (e.g. `neocom-back`, `neocom-front`) — not a GitHub Actions variable |

**Main / prod tagging:** when publishing from `main`, the workflow SHALL create an annotated git tag `v{majorMinorPatch}` on that commit (aligned with the SemVer bump table and `tag-prefix: v` above). Sample force-update of tags stays with `/neocom-git` — do not invent a force rule here beyond creating the version tag.

**Prod deploy validation (when a deploy job selects an image):** for `prod`, the requested image version SHALL match an existing **git tag** (`vX.Y.Z`); for non-prod (`staging` / other), the image version SHALL exist in GHCR (pull check) — same idea as the sample `calculate-image-tag` action, mapped to NEOCOM env names.

## Section 09 — Logging

Front and back logging SHALL share the same **contract shape**: every log call carries a **log level**, a **section**, and a **message**. Which lines are emitted is controlled by **configuration** (not hard-coded in call sites).

**Shared call contract:** callers SHALL pass level + section + message on each log. The runtime filters by the configured level for that section (and any documented global floor). Output that is emitted SHALL still include those three fields so logs remain filterable after the fact.

**Message placeholders:** the message MAY contain **placeholders**. Callers MAY supply **additional parameters**; the logger SHALL replace each placeholder with the **JSON representation** of the corresponding parameter before emission.

**Log levels:** the programme log levels are `**DEBUG`**,** `**INFO`, and `**PRODUCTION`**. Configuration for a section MAY also be set to** `**NONE`.

| Level        | Role                                                                                      |
| ------------ | ----------------------------------------------------------------------------------------- |
| `DEBUG`      | Development / diagnostic detail                                                           |
| `INFO`       | Informational messages                                                                    |
| `PRODUCTION` | Production-signal messages; SHALL **not** be filtered out even on production environments |
| `NONE`       | Configured section level meaning that section SHALL **not** generate logs                 |

**Production default:** on a **production** environment, the configured log level for sections SHALL default to `**NONE`** (no logs from those sections unless configuration raises the level). `**PRODUCTION`**-level log calls remain unfiltered on production environments (they still emit).

**Front — provider API:** `neocom-front` SHALL expose logging through a **provider API** (injectable / replaceable). Application code SHALL log via that provider, not via ad-hoc `console.`*. Configuration SHALL decide which sections and levels are shown so developers can quiet or open areas without code changes.

**Front — destinations:** when a front log passes the section/level filter, the provider SHALL send it to the **browser console**. **Server-front / host logging** (`server.js`, file sinks, npm-terminal bridging) is a **separate question** and is **not specified** in this section yet.

**Front — npm / terminal output (fact for designers):** Angular application code runs in the **browser**. Programme logs emitted by the front provider therefore appear in the **browser DevTools console**, not in the terminal that runs `npm start` / `ng serve` / watch. That npm terminal shows the **Node/CLI process** (compile, serve, HMR). Separately, `server.js` (Node Express static + proxy; see [Section 13](#section-13--local-configuration)) may write **its own** process `console` lines to that same terminal — those are host/proxy logs, not the Angular provider’s programme logs. **No bridge from browser programme logs into the npm terminal is specified yet.**

**Back — sectioned config:** `neocom-back` SHALL read a **configuration file** that sets the log level per **section**. Log control is by **level** and **section** only (no separate hierarchy requirement). The same level + section + message fields apply on every back log call.

**Back — line format (Spring Boot–like):** emitted back log lines SHALL be **properly formatted** with fields in the spirit of Spring Boot logging (readable, consistent columns/keys), including at least: **timestamp**, **log level**, **section** (logger / category), **message**, and **trace-id**. Additional Spring-like fields (for example thread / async-context label, application name) MAY be included when useful; the exact pattern string is not fixed here.

**Back — request trace-id (MDC equivalent):** for **traceability**, every **inbound HTTP request** SHALL create a new `**trace-id`**. That `trace-id` SHALL appear on log lines produced while handling that request, and SHALL be **accessible to all processes** that run for that request (inbound adapters, application use cases, domain, outbound adapters, and any async work that continues the same request scope).

**NestJS note (Spring** `MDC` **equivalent):** Spring Boot stores request fields in **MDC** (Mapped Diagnostic Context) and the logging pattern prints `%X{…}`. NestJS / Node has no built-in MDC; the programme equivalent is a **request-scoped async context** — typically Node `**AsyncLocalStorage`**, often via a Nest wrapper such as** `**nestjs-cls` (CLS = continuation-local storage). Middleware (or an interceptor) SHALL enter that store at request start, put `trace-id` in it, and the logger SHALL read `trace-id` from the store when formatting lines. Call sites SHOULD NOT have to pass `trace-id` manually on every log call.

**Gaps (do not invent until decided):** front section catalog names; concrete config file path / schema; whether back env vars (`LOGLEVEL` / `LOG_LAYERS` style) remain as overrides beside the config file; exact placeholder token syntax (only that placeholders are replaced by JSON of the matching parameters); whether a non-production default section level is fixed or environment-specific beyond the production → `NONE` rule; **server-front / host logging** (`server.js`, file sinks, npm-terminal bridge — not specified yet); exact back log **pattern string** / layout; whether `trace-id` is also returned on HTTP response headers; CLS library choice (`AsyncLocalStorage` direct vs `nestjs-cls` or equivalent).

### Front step types (from Printer3D Cypress pattern)

The front catalog SHALL cover these **step families** (parametrized; one family, many pages/panels):

| Family | What to test / do | Typical Gherkin role |
| ------ | ----------------- | -------------------- |
| Application bootstrap | Viewport, visit root, assert app shell exists | Given / When |
| Feature / dock navigation | Click a named feature; assert destination **page** or **dialog** | When / Then |
| Page activation | Assert a named page is active; set Cypress aliases `@target-page` / `@target` | Then |
| Page structure | Assert panel count and section count on a page | Then |
| Dialog lifecycle | Dialog opens and blocks display; dialog closes | Then / When |
| Target selection | Set `@target` / `@target-panel` to a panel type, a render/item by id, or a nested named field | Given |
| Field content | Assert field **label** and **value** (and hidden named fields) via `cy-`* | Then / Given |
| Actions | Click named button / actionable image; assert enabled/disabled / tag colour / missing | When / Then |
| Selection / variant | Assert selected state; assert render variant | Then |
| Counts | Assert target has N children of a symbolic type (or none) | Then |
| Loading | Loading message shown; loading completes | Then / When |
| Forms | Fill named inputs; submit when valid | When |

Symbolic names in steps (page / panel / render / dialog) SHALL be mapped to stable DOM selectors (component tags or `cy-*`) through a **translation table** (Printer3D `SupportService.translateTag` pattern) so versioned component renames do not rewrite every scenario.

### Required `cy-*` attributes (pages, sections, panels, renders)

UI under acceptance test SHALL publish these attributes so catalog steps can locate and assert without brittle CSS. Programme list (Printer3D practice + §01):

| Attribute | Where | Purpose |
| --------- | ----- | ------- |
| `cy-name` | Fields, buttons, actionable images, feature labels, drop areas, and other interactive or assertable nodes inside panels/renders | Primary named locator (`[cy-name="…"]`) |
| `cy-field-label` | Label element for a field on a panel/render | Assert published label text |
| `cy-field-value` | Value element for a field on a panel/render | Assert published content / UI value |
| `cy-section-name` | **Sections** on a page | Locate a named section (programme; see §01) |
| `cy-field-mark` | Optional mark / badge on a render or panel | Assert visual mark state when used |
| `cy-input-type` | Editable field wrappers | Distinguish input kinds in form steps |
| `cy-focus` | Inputs that require focus/blur behaviour in tests | Drive focus-related interactions |
| `cy-dialog` | Dialog roots when not identified solely by component tag | Locate blocking dialogs |

**Scope of publication:**

| Surface | SHALL expose |
| ------- | ------------ |
| **Page** | Stable identity (component tag and/or page-level `cy-`*); enough structure for panel/section counts |
| **Section** | `cy-section-name` (or equivalent stable section locator used by catalog steps) |
| **Panel** | Stable identity for target-selection steps; nested fields with `cy-name` / `cy-field-label` / `cy-field-value` as needed |
| **Render** (domain node viewers) | Same field attributes as panels for every assertable field; `cy-name` on actions; optional `cy-field-mark` |

Do not invent additional `cy-*` names in scenarios beyond this list until the catalog is extended deliberately.

## Section 11 — Continuous integration pipeline

CI Node/jobs/workflows/secrets (legacy OpenSpec numbering INFRA-030…039 in that change — **not** L0 executive card ids). Rows are `[ ] to review` until re-extracted into `front-cicd` / `back-cicd`.

### Pipeline shape (front and back)

Each of `neocom-front` and `neocom-back` SHALL have a CI pipeline that runs the following **ordered stages**. **Lint / format** SHALL run **after setup and before testing**. **Unit testing** and **acceptance testing** MAY run **in parallel** after lint passes (see [Section 04](#section-04--cicd-test-jobs-and-sonar-gate-order)). Sonar, Packages publish, and the Docker image step SHALL wait until the parallel test stage has passed.

**Workflow triggers:** the product caller workflows (and thus testing / the full CI pipeline) SHALL run on pushes and pull requests for `feature/`**, `develop`, and `main`, and on **all git tags** (`tags: ['*']` or equivalent).

| Order | Stage | Notes |
| ----- | ----- | ----- |
| 1 | Setup (Node from `.nvmrc` / `neocom` pin) | Shared setup action |
| 2 | **Lint / format** | First quality step after setup; SHALL complete successfully before any test job starts (once those scripts are defined) |
| 3a / 3b | **Unit testing** ∥ **Acceptance testing** | Parallel jobs after lint. Front acceptance = Cypress + Cucumber (+ WireMock; no live `neocom-back`). Back acceptance = Gherkin/Cucumber (OpenAPI / API) per [Section 06](#section-06--backend-testing) |
| 4 | **Sonar** project upload + quality-gate validation | After both test jobs succeed; uses per-repo `sonar-project.properties` (org + Sonar data) + workflow `SONAR_PROJECT_KEY`; project must exist beforehand ([Section 03](#section-03--coverage-control-and-quality-gates) / [Section 04](#section-04--cicd-test-jobs-and-sonar-gate-order)) |
| 5 | **Publish** versioned artifact to **GitHub Packages** | After Sonar gate passes; `commitTag` / `imageTag` per [Section 08](#section-08--deployment) (`main` → plain MajorMinorPatch + git tag `vX.Y.Z`; other branches → `{mmp}{preReleaseLabelWithDash}.{shortSha}`) |
| 6 | **Build Docker deployable image** | Tag `{artifactName}:{imageTag}`; push `ghcr.io/{owner}/{artifactName}:{imageTag}` and `:latest` (§08 naming contract) |

The production build remains part of the pipeline; it MAY run after lint and before or alongside the test stage as the reusable actions define, but a failed build SHALL fail the pipeline.

### Reusable actions in `neocom-meta` (feasible)

**Feasible and already in use.** Product repos keep **thin caller workflows** under their own `.github/workflows/`. Encapsulated steps live in `neocom-meta` as:

- **Composite actions** — `AdamAntinoo/neocom-meta/.github/actions/<name>@<ref>` (one action per feature: setup-node, unit-test, acceptance-test, sonar-gate, publish-packages, build-docker-image, …)
- **Reusable workflows** — `AdamAntinoo/neocom-meta/.github/workflows/<file>.yml@<ref>` (job graphs called with `jobs.<id>.uses`)

Proven pattern today: `neocom-front/.github/workflows/build.yml` calls `neocom-meta/.github/workflows/front-build.yml`, which uses meta composite actions (`setup-node-environment`, `front-production-build`).

**Constraints:** callers must grant needed `permissions` (e.g. `packages: write` for publish). For a **private** `neocom-meta`, GitHub requires Actions access policy so front/back may use its workflows/actions; prefer pinning a tag or SHA rather than a long-lived branch once stable. Secrets stay in each product repo’s host secret store (or org secrets); composite actions cannot declare secrets — callers pass them into reusable workflows when needed.

### Local Docker engine handoff (not on github-hosted runners)

GitHub-hosted workflow jobs **cannot** talk to the developer’s / lab **local Docker engine**. Therefore:

1. **CI (github-hosted)** builds the image and **pushes it to GHCR** (GitHub Packages).
2. **Deploy onto the local Docker engine** is a **post-CI** step on the machine that owns that engine, using one of:
   - **Preferred default:** a **local post-action script** (e.g. `gh` auth + `docker pull ghcr.io/…` + `docker compose up` / run) triggered after a successful CI run (manual, cron, or CI status webhook); or
   - **Alternative:** a **self-hosted runner** on that host, with a small **deploy-only** workflow job that pulls the published image and starts it on the local daemon.

Do **not** put “deploy to local Docker” on a github-hosted job. Exact script name / compose layout stays open until authored; do not invent paths here.

### GitHub project configuration (secrets, committed workflow config, permissions)

**Design rule — minimise manual GitHub UI configuration.** Non-secret CI values SHALL live in the **committed product-repo workflow definitions** (and related committed files such as `sonar-project.properties` / `.nvmrc`), not in GitHub Actions **repository variables**. Developers SHOULD only need to set **secrets** and a few **repository/org settings** once. Prefer **Organization** secrets when the value is shared across repos. **Never commit** secret values.

**Sonar projects SHALL be created beforehand** in SonarCloud (or SonarQube). **Organization and other Sonar analysis data** SHALL live in each product repo’s committed `sonar-project.properties` (consumed by the Sonar upload action). The **Sonar project key** SHALL be set in the **local caller workflow** configuration (`env:` / job inputs — not GitHub Actions Variables UI).

**Pinned Sonar keys (programme):**

| Repo | Organization (`sonar.organization` in `sonar-project.properties`) | Project key (local workflow `SONAR_PROJECT_KEY`) |
| ---- | ----------------------------------------------------------------- | ------------------------------------------------ |
| `neocom-front` | `adamantinoo` | `AdamAntinoo_neocom-front` |
| `neocom-back` | `adamantinoo` | `AdamAntinoo_neocom-back` |

GHCR `artifactName` values remain committed in each caller workflow when those stages land (e.g. `neocom-front` / `neocom-back`).

#### Workflow `permissions` (in caller YAML, not the secret store)

Each caller workflow that publishes or pushes images SHALL declare at least:

| ---------- | ---- |

| `packages: write` | GitHub Packages publish and GHCR push |
| `pull-requests: write` / `checks: write` | If Sonar (or other) decorates PRs / checks — enable when that integration is turned on |

`GITHUB_TOKEN` cannot be elevated by a called reusable workflow beyond what the caller grants. Permissions blocks live in the **committed** caller YAML.

## Section 13 — Local configuration

Moved from former OpenSpec `infra-local-config` / `infra/local-config` (INFRA-020…026). Rows start at `[ ] to review` until re-extracted. Do not invent WireMock port or stub paths before stubs exist.

**Named environments (consistent names):** programme environment names SHALL be `**dev`**,** `**staging`, and `**prod`**:

| Name          | Meaning                                                                                       |
| ------------- | --------------------------------------------------------------------------------------------- |
| `**dev**`     | Local developer start (`start:dev`) for **manual** developer testing; uses real `neocom-back` |
| `**staging**` | Docker deployment for the `**develop**` branch                                                |
| `**prod**`    | Docker deployment for final / production from the `**main**` branch                           |

`**dev` vs mock:** `**dev`** SHALL use the **real** `neocom-back` configuration. **WireMock / mocks** are for **automated testing only** (see [Section 02](#section-02--mock-data-from-real-runs)), not for `dev` manual testing. **Removed:** CICD-F-100 (former INFRA-020 — front `dev` pointed at WireMock and not at `neocom-back`); CICD-F-104 (former INFRA-024 — parent `neocom` git submodules; deprecated).

`neocom-front` has **two run modes**:

1. **Watch** — compiles on the fly; used for local `dev` and related local work.
2. **Server** — starts the application with `neocom-front/server.js`; used for deployed hosts (`staging` / `prod` style) and production-style running.

**Port ranges (front services):** each environment SHALL use a **different** port decade so services do not collide. Exact port numbers inside a decade are assigned per service when pinned; do not invent specific service→port maps here beyond the ranges.

| Environment                                       | Port range         |
| ------------------------------------------------- | ------------------ |
| `**dev**` (local `start:dev`)                     | `600x` (6000–6009) |
| `**staging**` (Docker / `develop`)                | `601x` (6010–6019) |
| `**prod**` (Docker / `main`)                      | `602x` (6020–6029) |
| **Testing** (different front services; automated) | `609x` (6090–6099) |
