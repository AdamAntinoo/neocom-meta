## Goals
Testing is a most importan part of the development process. This project will use SDD->BDD->TDD desing model so from spec we should create gherkin scenarios that should be validated before the feature is completed. The gherphin will be done with the cypress tool that should validate flows and also the UI validity of the pages and panels found. For thesting the system should provide mocked scenarios and configurations that allow to test the elements with predefined and stable data so adapters should be configurable and replaceable on the testing environment

## Cypress UI and content validation

Cypress testing SHALL validate not only navigation flows but also the **contents** of panels and items and their **UI aspects**. That includes colour and other visual or structural properties that the application publishes for tests through the documented `cy-*` attributes (for example `cy-section-name`, `cy-field-value`, `cy-field-label`, `cy-name`, and any further catalogued Cypress properties).

Gherkin scenarios that cover a page or panel SHALL assert against those published properties so content and UI validity are checked with stable selectors before the feature is considered complete. Pages and panels under test SHALL expose the relevant `cy-*` properties so Cypress can locate and verify them.

## Mock data from real runs

Testing SHALL use **mock data extracted from real runs** so scenarios can cover realistic variations and UI aspects. That includes the appearance of **errors** and the presentation of **stale** or **incorrect** data, not only happy-path payloads.

Captured fixtures SHALL be stable and predefined for the test environment (via configurable, replaceable adapters) while still reflecting shapes and edge cases observed in production-like or developer runs. Gherkin scenarios SHALL be able to select those fixtures so Cypress can validate how pages and panels render each variation.

## Coverage control and quality gates

The project SHALL provide a **tool to measure and control code testing coverage**. Coverage results SHALL be available to developers locally and in CI so gaps can be found before a feature is completed.

The project SHALL define **quality-gate rules** that use coverage (and related test outcomes) to pass or fail a change. A feature SHALL NOT be considered complete when required gates fail. Gate thresholds and which suites they apply to (unit, acceptance/Cypress, and any later layers) SHALL be recorded so agents and CI enforce the same rules.

NEOCOM projects SHALL **report to SonarCloud** so coverage, quality gates, and other quality findings are checked in one place. CI SHALL upload analysis (and coverage where applicable) to SonarCloud; a change that fails the configured SonarCloud quality gate SHALL NOT be considered complete.

## CI/CD test jobs and Sonar gate order

CI/CD SHALL run **unit testing** and **acceptance testing** as **separate tasks** that **MAY run in parallel**. Both SHALL complete successfully before the **SonarCloud analysis / quality-gate** step. The Sonar gate SHALL NOT start until those test tasks have passed (and their coverage artifacts are available when the analysis requires them).

## Testing command catalog

There SHALL be a **catalog of stable, common testing commands** shared across NEOCOM projects. Names SHALL be **short and clear**. Front and back MAY differ in how each command is implemented, but the catalog names and intent SHALL stay the same so agents and developers use one vocabulary.

The catalog SHALL cover separately:

| Layer | Intent | Tooling (current) |
| --- | --- | --- |
| **TDD** | Unit testing | Project unit runner (e.g. Vitest on front, Vitest on back) |
| **BDD** | Acceptance testing | Cypress with Gherkin |
| **SDD** | Integration / full automated UI testing | Defined later; SHALL cover cross-cutting automated UI tests beyond acceptance scenarios |

Each catalog entry SHALL include the **environment setup** required to run that layer (for example Node/nvm, WireMock or mocks, app under test, Cypress binary). There SHALL also be a command that runs **all testing layers in sequence** (TDD, then BDD, then SDD when defined), after applying the setup each layer needs.

## Backend testing

`neocom-back` SHALL follow the **same testing guidelines** as the front (SDD→BDD→TDD, coverage and quality gates, SonarCloud, shared command catalog intent, mock fixtures from real runs where applicable).

Backend acceptance and integration scenarios that need **stable, predefined data** SHALL use **mocked sources**, with **WireMock** (or an equivalent HTTP mock) replacing upstream dependencies for those scenarios. **Universe ESI** reference data MAY use **real ESI feeds** when that is acceptable for the scenario. Every other external source SHALL be decided **case by case** (mock vs live), and the choice SHALL be recorded for that scenario.

Backend BDD acceptance tests SHALL use **Gherkin** with **Cucumber** (or another BDD runner that consumes the same Gherkin scenarios) so acceptance behaviour is expressed the same way as Cypress-driven front acceptance.

## Domain node unit tests

Front **domain NeoCom nodes** (classes that inherit from `NeoCom` / `NeoComDelayed` — EPIC-002 [Domain module](./02.EPIC-ANGULAR-CODIFICATION.md#domain-module-neocom-nodes), today under `innovative-core/domain` pending move to `modules/domain`) have **no systematic unit-test definition**. Render specs alone do not cover node construction, accessors, `jsonClass`, hierarchy/`children`, or wire/`fromDto` mapping.

The TDD process SHALL **review** each domain node and **create** Vitest unit tests where they are missing or incomplete.

| Concern | Expectation |
| --- | --- |
| Scope | Every front NeoCom node class in the domain module (flat first-level files and later classified folders) |
| Runner | Front unit runner (**Vitest** / `ng test`) — same TDD layer as the testing command catalog |
| Review | Inventory nodes; note which already have adequate `*.spec.ts` coverage and which lack it |
| Create | Add or complete co-located `*.spec.ts` (or an agreed suite) for gaps found in that review |
| Minimum behaviours | At least: construction / `fromDto` (or equivalent), `jsonClass`, identity getters used by renders, and any node-specific collaboration / children rules the class owns |
| New nodes | A new domain node SHALL ship with unit tests in the same change (TDD); do not leave new nodes without a suite |

| ID | Review | Requirement |
| --- | --- | --- |
| DNODE-001 | [ ] to review | The testing process SHALL **review** all front domain NeoCom node classes for unit-test coverage and record gaps |
| DNODE-002 | [ ] to review | For each domain node lacking adequate unit tests, the process SHALL **create** Vitest unit tests covering construction/mapping, `jsonClass`, and the accessors / behaviours that renders and panels rely on |
| DNODE-003 | [ ] to review | New domain NeoCom nodes SHALL include unit tests in the same delivery as the node class (TDD); domain nodes without a defined unit suite are incomplete |
| DNODE-004 | [ ] to review | Domain-node unit tests SHALL live with the domain module (co-located `*.spec.ts` or an agreed domain test folder) and run in the standard front unit-test CI job |
